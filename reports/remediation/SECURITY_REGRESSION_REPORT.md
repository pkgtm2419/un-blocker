## 3. Deep Security Mechanics

### 3.1 Cryptographic Anti-Spoofing (RFC 5452)
In [DnsUpstreamClient.kt](file:///d:/un-blocker/app/src/main/java/com/unblocker/app/services/DnsUpstreamClient.kt#L54-L59):
```kotlin
// Cryptographically randomize outbound upstream transaction ID (SEC-02, RFC 5452 anti-spoofing)
val upstreamTxId = txIdGenerator() // SecureRandom.nextInt(0x10000)
val upstreamPayload = dnsPayload.clone()
upstreamPayload[0] = ((upstreamTxId.toInt() ushr 8) and 0xff).toByte()
upstreamPayload[1] = (upstreamTxId.toInt() and 0xff).toByte()
val upstreamQuery = query.copy(transactionId = upstreamTxId)
```
- Every outbound query replaces the client-side TxID with an entropy-rich cryptographic TxID generated by `java.security.SecureRandom`.
- Inbound responses must match this upstream TxID exactly; otherwise, they are discarded by `DnsResponseValidator`.
- Before delivering the response to the client app, the original client TxID is restored (`restoreClientTxId`).

### 3.2 Thread Isolation & Cross-Request Non-Contamination
With 16–32 worker threads executing in parallel, each query is encapsulated in its own immutable `DnsQuery` and `toForwardingRequest()` value object.
- Request coalescing in `DnsRequestCoalescer` uses thread-safe atomic data structures (`ConcurrentHashMap`).
- When a leader query resolves, only waiters registered for that exact coalescing key receive copies of the response with their respective client TxIDs restored.
- In `DnsConcurrencyStressTest`, 250 parallel queries across 50 threads each verified that 100% of received responses matched their own query domain and original TxID.

### 3.3 Trapped DNS Servers Isolation
In `TrappedDnsServers.kt`:
- Well-known hardcoded DNS server IPs (`8.8.8.8`, `1.1.1.1`, `9.9.9.9`, etc.) commonly hardcoded in hostile apps to bypass system DNS are intercepted and redirected to the local filtering engine.
- Outbound forwarding only occurs to validated system resolvers.
