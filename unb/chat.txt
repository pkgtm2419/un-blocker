Un-Blocker: Android 16 & 17 Security and Performance Audit
Conditional recommendation
Reviewed: 11 November 2026

Application: Un-Blocker by pkgtm2419

Latest published release: v2.6.1, released 10 November 2026.

Initial verdict: This is a genuine DNS-based ad-blocking application, not a conventional VPN service. Its architecture can block advertising and tracking domains across Android apps without rooting your device. However, it cannot block every type of advertisement, and its real-world effectiveness has not been established by an independent, comprehensive benchmark.

The important distinction is between an application that can block ads and one that has been proven safe and effective across Android devices. I'll assess those separately.

 The application's configuration permits installation on newer Android versions, but installation compatibility is not proof that its DNS filtering, background service and VPN lifecycle work correctly.

There is a significant testing gap: the repository's Android device-test matrix covers API 26, 30 and 35, not API 36 or 37. The app also compiles against SDK 35, despite older README text referring to SDK 36.

That means I cannot certify reliable operation on either Android 16 or Android 17 from the available automated tests.

Findings that matter most
1. The v2.6.1 APK is test-signed, despite being labeled a production release.

I inspected the successful GitHub Actions release run. Its logs explicitly state that production keystore secrets were unavailable and the process fell back to stable test signing.

The APK signature was subsequently verified against that test certificate, so this is not evidence of malware. But production signing provenance is weaker than the release description suggests.

Evidence: v2.6.1 release pipeline logs and release workflow.

2. DNS logging is enabled by default.

The application records readable domain names and aggregate request counts in a local Room/SQLite database. Aggregate records have a 30-day retention policy; detailed chronological event history requires opt-in.

This is not the same as uploading browsing history to a developer's server, and I did not find a telemetry upload mechanism in the reviewed filtering path. However, local domain history is not encrypted at the application database layer. It is principally protected by Android's app sandbox and device security.

The app's privacy documentation describes these local logs, but some promotional and code comments still imply that no domain history is stored.

Evidence: QueryLogSink.kt, database provider, privacy policy.

3. Release quality checks need strengthening.

The app's Gradle configuration contains abortOnError = false, ignoreWarnings = true, and disabled lint checks. This weakens automated quality enforcement.

The project does have positive evidence: the v2.6.1 release build, unit-test workflow and CodeQL analysis completed successfully. But a scheduled device-matrix run on 10 November failed during job setup, before its Android emulator tests ran. That failure does not prove an application defect, but it also cannot be counted as a successful device test.

Evidence: Build configuration, Android checks and device matrix run.

I also found that a post-release commit removed many historical QA documents from main, while the README still links to some of them. The documents remain available in the v2.6.1 tag. This is a documentation and auditability weakness, not evidence by itself of malicious activity.
4. Performance and battery assessment
APK download size	5.56 MiB
DNS processing	Local filtering with caching and bounded work queues
Background operation	Persistent foreground VPN service
Mobile battery impact	Not independently measured
24-hour stability	No verified physical-device soak test for v2.6.1


The code uses a DNS cache, bounded queues, worker threads and limits on downloaded filter sizes. These are reasonable performance engineering choices.

However, the DNS resolver uses timeouts and retries. Under unreliable Wi-Fi or mobile-data conditions, upstream DNS failures could cause noticeable website or app-loading delays.

The repository's older performance reports describe fast local rule matching, but they do not establish current device-wide battery consumption, memory stability or end-to-end browsing latency on Android 16/17.

Another important point: the Extensions screen lists many third-party filter subscriptions. Most require an explicit download or enabled auto-update before their remote rule files become available. The displayed estimated filter counts should not be confused with verified, loaded rules.

Performance verdict: The architecture is lightweight enough to justify testing, but its real-world battery and reliability impact is still unverified.
5. My recommendation for your phone
I would not yet make Un-Blocker v2.6.1 my primary ad blocker on an Android 16 or 17 daily-use phone. The test-signed production-labeled release, missing current Android-version CI coverage, and locally stored DNS history are enough reasons for caution.
